# Access deployment split

Use one repository and three deployments. Render serves the Access plug-in, the public API and the Savanna reference demo at `https://access-plugin.onrender.com`. Two Vercel projects serve independent static host pages that install Access over HTTPS. This plan changes where demos run. Track 2 feature and review requirements still follow the [Track 2 plan](TRACK_2_IMPLEMENTATION_PLAN.md) and [judging plan](JUDGING_PIVOT_PLAN.md).

| Deployment | Repository source | Responsibilities |
| --- | --- | --- |
| Existing Render service | `https://access-plugin.onrender.com`; repository root, including `packages/lesson-component/`, `services/api/`, `services/core/`, and `examples/savanna/` | Serve the versioned lesson and career modules, OpenAPI, public fixtures, media and exports, and Savanna at `/` and `/demo/savanna`. |
| EthioWare Vercel project | `demos/ethioware/` | Own the EthioWare-style page, local CSS, and host controls. Embed the same lesson module used by Savanna. |
| Career Gateway Vercel project | `demos/career-gateway/` | Own the careers page, local CSS, and fictional certificate viewer. Embed the Access career module and fetch public fixtures from Render. |

The proposed `demos/` folders each contain an entry HTML page, their own assets, and a short README with local preview and Vercel settings. Keep the original Savanna fixtures and local development tools and test fixtures. Treat “only the plug-in infrastructure and Savanna demo” as the public Render surface. Move the independent installer flow to the embed documentation and retain its cross-origin test as a local fixture. Keep avatar review and the privacy/session demonstration in local tooling where needed for review or testing. Review every existing public route and asset mount before removing exposure, including direct access to old demo assets. See [contributor instructions](../../CONTRIBUTING.md) and the [repository security rules](../../.agents/rules/security.md).

## 1. Restore the shared release on Render

The current `main` tree contains the [career component](../../packages/lesson-component/src/career-element.ts), [job fixtures](../../services/core/src/access_core/jobs.py), and [API tests](../../services/api/tests/test_career_gateway.py). The [build](../../packages/lesson-component/package.json) omits the careers entry point, and the [API](../../services/api/src/access_api/main.py) omits the jobs and certificate endpoints. The two public Render demo URLs returned 404 when checked. Moving the HTML alone would leave the career demo without its data and component.

- Restore the `jobs.js` build entry and generated integrity metadata. Review the focused changes from historical commit `e73cbb3` for the career build and API, excluding unrelated session and security changes. Before a Vercel host is promoted, `https://access-plugin.onrender.com/components/0.1.0/jobs.js` and `https://access-plugin.onrender.com/components/0.1.0/integrity.json` must both return `200` from the deployed release.
- Restore `GET /api/v1/jobs`, `GET /api/v1/jobs/{job_id}/structured-data`, and `GET /api/v1/demo-certificates/{identifier}` using the existing fictional data and response schemas. Publish them in OpenAPI. Keep certificate status server-controlled and preserve the unknown-ID and cache behavior covered by the existing tests.
- Verify that the same lesson release works in Savanna and off origin, including lazy-loaded chunks, caption and media URLs, and exports. Publish the external embeds under a new immutable release URL if the bytes differ from the existing release. Record the exact lesson and jobs integrity hashes in the installation instructions and pin them in the Vercel pages.
- Configure `ACCESS_ALLOWED_ORIGINS` with the two exact stable Vercel origins once assigned. Keep public requests credential-free. Verify the script, its imported chunks, API results, and media from each origin under the hosts' content security policies. Add a specific preview origin when a preview must be used for testing.

## 3. Verify before switching traffic

1. Build and typecheck the component, run the API suite and the relevant Playwright tests, and run repository and security baseline checks. Implement redirects behind deployment configuration and test them with example destinations before enabling them. Replace tests that expect Render to return partner HTML. Serve each Vercel output on its own local HTTP origin during browser tests and use the real shared API to exercise embedding, CORS and SRI.
2. Deploy the reviewed shared release to `https://access-plugin.onrender.com` with the public fixture APIs and approved origins. Confirm `/healthz`, `/components/0.1.0/integrity.json`, `/components/0.1.0/lesson.js`, `/components/0.1.0/jobs.js` and `/api/v1/jobs` return `200` before publishing both static Vercel projects. Open each public URL in a clean browser and confirm modules and API data load. Test Savanna captions, transcript seek and downloads. Repeat transcript seek and downloads on EthioWare. On Career Gateway, test keyboard search, filters, job details and fictional certificate states, including an unknown ID and direct refresh. Check mobile layout, fallback links and error states.
3. After both public sites pass, enable temporary redirects from Render `/demo/ethioware` and `/demo/careers` to the corresponding stable Vercel URLs. Preserve access to existing fictional certificate deep links by redirecting `/demo/certificates/{identifier}` to the corresponding Career Gateway page. Use fixed, deployment-configured HTTPS destinations. Redirect paths must never accept a destination from a request. Update the demo links, [deployment guide](../setup/DEPLOYMENT_AND_LOCAL_DEMO.md), and [career demo guide](../architecture/CAREER_AND_PROVIDER_DEMOS.md).
4. Keep the previous working Render release and each Vercel deployment available for rollback. If a host fails, restore its previous deployment or suspend its redirect. Keep the shared public endpoints and pinned plug-in release available while either site uses them.
